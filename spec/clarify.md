# Senior Review: Specification Gaps and Clarifications

## Review Summary

The feature scope and primary dashboard behaviors are understandable, but the specification is **not ready for implementation**. The principal blocker is access control: the requirements combine a separate web application, Jira-native visibility, no separate application authorization model, and a proposed service-account authentication approach without defining how a viewer's Jira permissions are preserved if data is persisted and served by the application. Other blocking choices include the external-stakeholder data policy, Jira/API configuration, sprint/status/issue semantics, and refresh behavior.

This review compares [constitution.md](./constitution.md), [specification.md](./specification.md), and the source requirements in [project_spec.md](../project_spec.md). Priorities below indicate implementation risk, not delivery order.

## Contradictions and Requirement Tensions

| ID | Priority | Evidence | Finding |
|---|---|---|---|
| C-01 | P0 | Source `project_spec.md` §2 says external stakeholders must receive “full dashboard access”; §8 leaves open whether they receive issue-level data or summary only. Specification FR-016 and User Story 4 defer external access to an unconfirmed organization policy. | The source both promises full access and leaves the extent of data access undecided. The new specification does not resolve whether “full dashboard access” means full feature functionality, all configured dashboard data, or full Jira issue details. |
| C-02 | P0 | Constitution §2 requires the Express backend to own authorization enforcement. Specification FR-015 and Out of Scope prohibit a separate application-level authorization model; FR-015 also requires Jira-native visibility. | These can coexist only if “authorization enforcement” means faithfully applying Jira's per-viewer permissions rather than defining application roles. The specification does not define identity propagation or permission checks for a standalone app, so the two requirements currently have no implementable reconciliation. |
| C-03 | P0 | Specification FR-003/FR-015 and Access, Security, and Data Handling require server-side Jira access, Jira permission parity, and no data exposure beyond a viewer's Jira permissions. FR-013 requires PostgreSQL for application data; the access section warns that a backend service account and shared database must not widen visibility. | If Jira data is synchronized into shared persistence, the service-account approach does not, by itself, preserve per-viewer Jira permissions. The spec recognizes this risk but does not choose a viable identity/delegation or per-viewer filtering and storage-isolation design. |
| C-04 | P1 | Source `project_spec.md` §2 requires full dashboard access for external stakeholders; the specification's open question 5 permits issue-level data **or** summary-only data. | It is unclear whether external stakeholders are expected to see the same data and issue details as internal users, or only the same dashboard features. Resolve explicitly; do not treat authorization as an implementation detail. |
| C-05 | P1 | Constitution is for Jira/Confluence automation; specification Summary and Out of Scope expressly exclude Confluence. | This is reasonable for a Jira-dashboard feature, but it does not satisfy or define the broader Jira/Confluence project scope. Confirm that this file specifies only one feature and identify whether Confluence needs a separate specification. |
| C-06 | P1 | User Story 1 describes planned, in-progress, complete, **or blocked** work. FR-008 defines only To Do, In Progress, and Done, and no requirement defines a blocked indicator or mapping. | “Blocked” is part of the promised user outcome but has no data source, definition, or display behavior. Clarify whether it is a separate Jira field/status, a label, part of In Progress, or not in scope. |
| C-07 | P1 | Source formula uses completed issues / total issues **in a sprint**. FR-009 changes the denominator to “the selected sprint scope”; the dashboard also shows all sprints and can filter projects, assignees, and issue types. | The per-sprint formula is clear, but the aggregation and denominator when multiple sprints or filters are selected are not. A portfolio-wide percentage could differ from a per-sprint percentage or an average of sprint percentages. Define the displayed calculation for each view. |

## Recommended Clarification Order

Resolve these before planning implementation:

1. **Access model**: application sign-in, viewer identity, Jira permission parity, external-user policy, issue-level versus summary-only visibility, and safe cache/storage model.
2. **Jira contract**: target URL/version/API, project/board scope, field mappings, sprint discovery, status mapping, and permitted data.
3. **Metric semantics**: issue population, duplicate/sub-task treatment, meaning of Done, blocked work, and filtered/multi-sprint aggregation.
4. **Refresh contract**: data shown during refresh, stale-data behavior, schedule window/time zone, failure/partial results, retry, and recovery.
5. **Product interaction**: exact metrics, timeline behavior, filter combination, issue identification/navigation, and empty/loading/error states.
6. **Persistence and operations**: PostgreSQL data/retention, configuration ownership/review, deployment/scheduler environment, and measurable verification targets.
7. **Scope confirmation**: confirm this is specifically the Jira dashboard feature and whether Confluence requires a separate feature specification.

## Source Wording Note

The source acceptance criterion “The dashboard displays issued completion percentage” appears to contain a typo; the specification interprets it as “issue completion percentage.” Confirm only if the source author intended a different metric.
