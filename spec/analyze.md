# Task Analysis: Jira Sprint Dashboard Prototype

- **Reviewed**: 2026-11-04
- **Inputs**: [specification.md](./specification.md), [plan.md](./plan.md), [tasks.md](./tasks.md), and [constitution.md](./constitution.md)
- **Scope**: The 16 actionable PT tasks in the current mock-only prototype task list. Production Jira tasks are assessed as deferred/blocked gates, not as prototype implementation work.

## Summary

The current task list is a substantial scope reduction from the earlier live-Jira backlog. It describes a synthetic-data prototype across five phases and includes acceptance criteria and dependencies for all 16 PT tasks. The highest implementation risks are not Jira integration complexity (which is explicitly excluded) but unresolved product scope, an unassigned toolchain decision, and inconsistency between prototype-level decisions and still-active production requirements elsewhere in the specification.

Complexity estimates below reflect the task as currently written, not elapsed time. “Dependencies” lists direct task or milestone prerequisites from `tasks.md`; phase/milestone gates in `plan.md` also apply.

## Cross-Document Review

### Contradictions and Scope Tensions

1. **Prototype decisions versus full product requirements — High.** `specification.md` adds a clear G-01–G-14 prototype decision table, but its Summary, User Stories 1–4, FR-001–FR-019, Quality and Verification, SC-001–SC-009, and Open Questions still describe live Jira access, users, issue data, filters, metrics, refresh, persistence, and scheduled work in normative terms. The plan/task list correctly defer much of this for the prototype, but document consumers may still read those requirements as active. Mark them explicitly as future-product scope or identify prototype-specific acceptance requirements and status for each FR/SC.
2. **User Story 1 and FR-006/FR-009 versus prototype metric exclusions — High.** The product requirements promise status distribution and completion; prototype G-06/G-10 defer completion and additional metrics, while G-08 excludes UI criteria. PT2.2 says not to calculate completion and PT3.1 presents only approved non-issue-level information, but it is unclear whether status distribution itself is an approved prototype output. Clarify that boundary before UI implementation.
3. **FR-001 and FR-003 versus G-03/G-07 — High.** FR-001 says the product retrieves Jira data via Jira Server API, and FR-003 says the browser communicates with Express for Jira data. The prototype decision table forbids live Jira and dashboard-data API flow. The plan resolves this by limiting the plan to the prototype, but the spec should label these FRs as future scope for the prototype.
4. **Database mandate versus no persisted prototype data — Medium.** The constitution mandates PostgreSQL 15 via Docker, and plan Phase 1 / PT1.2–PT1.3 configures PostgreSQL and migrations, although prototype Jira-like data and any other persisted application data are expressly absent. This is constitution-compliant, but the plan should clarify whether starting PostgreSQL is a prototype acceptance requirement or merely a stack-foundation check, and whether an empty baseline migration is expected.
5. **Status distribution versus “non-issue-level” presentation — Medium.** G-05 confirms mapping categories for fixture data, but G-06 excludes completion metrics, and PT3.1 prohibits an issue list while requiring a prototype presentation of approved information. The scope does not explicitly approve aggregate status counts, so avoid assuming those counts are the desired display.
6. **G-15–G-23 dispositions — Medium.** The user confirmed decisions only through G-14. Specification language says the remaining findings are “undecided or deferred,” while PT0.3 asks to classify each as resolved/deferred/blocking. The plan and tasks should use a neutral unresolved status unless the user or responsible owner approves an out-of-scope disposition.

### Gaps and Missing Artifacts

- **Toolchain decision artifact and task — High:** Exact Node.js, Express, Vite, Docker Engine, and Docker Compose versions must be selected by the constitution before bootstrap. PT0.3 says they must already be selected and PT1.1 both bootstraps and mentions versions, but there is no distinct task or explicit decision artifact/template. Name the decision record and make version selection a prerequisite with a testable acceptance criterion.
- **Prototype acceptance baseline — High:** The plan calls for a local read-only demonstrator, but no approved screen regions or required data are specified, and G-08 explicitly excludes screen/layout acceptance. Agree on the minimum content (or explicitly approve a label-only/placeholder demonstrator) before PT3.1; otherwise “prototype presentation” is subjective.
- **Fixture schema and provenance — Medium:** PT0.2 defines categories and synthetic constraints but not the fixture's record shape or approval process. G-22 remains unresolved, so do not claim a representative fixture or source-of-truth counts. The acceptance criteria should test provenance without creating an unapproved Jira domain schema.
- **Backend purpose and verification — Medium:** The plan/task list require an Express backend, health/readiness, PostgreSQL, and migrations, but the mock fixture must not be served through that backend and there is no other application-data flow. Clarify that the backend is only a technology foundation for this prototype and define the minimal endpoint/DB readiness checks without adding dashboard functionality.
- **Acceptance evidence artifact — Medium:** PT4.3 asks for an evidence matrix, but no path/schema/owner is named and G-23 is unresolved. Specify a small artifact (for example a section in local handoff documentation) or record it as an unresolved release artifact; do not create an artifact that suggests unapproved sign-off.
- **Clarification review synchronization — Medium:** PT0.3 references G-15–G-23, but [clarify.md](./clarify.md) itself still records all findings as gaps needing answers. The report should point to the exact current dispositions and retain unresolved items instead of interpreting them.
- **Plan-to-task granularity — Low:** The task list covers each phase's work at a useful level, but it does not explicitly name a separate verification task for the PT2.1 fixture provenance/repository scan or for the PT1.2 Docker readiness check beyond their acceptance criteria. These can remain embedded criteria if evidence is recorded.

### Dependency and Traceability Review

- The task list contains **16 unique PT IDs** across Phases 0–4; direct PT dependencies resolve. Milestone dependencies (`M0`–`M3`) are additional gates and should be treated as prerequisites, not as PT IDs.
- **Phase 0 is internally coupled:** M0 requires PT0.4 (this analysis) and PT0.3 (decision/deferral classification); tasks PT1.1 onward depend on M0. This analysis can be prepared early, but should be rechecked against the final PT0.1/PT0.3 decisions before M0 is accepted.
- **Toolchain dependency is under-specified:** PT1.1 depends on M0 and PT0.3, while PT0.3 acceptance already requires toolchain versions selected. No task owns that selection independently, creating a practical blocker for PT1.1 if PT0.3 is interpreted literally.
- **Database ordering is coherent but perhaps unnecessary:** PT1.2 depends on bootstrap and PT0.3; PT1.3 depends on PostgreSQL; PT1.5 follows all quality/runtime setup. However, the schema/content purpose is absent by design, so acceptance should distinguish an infrastructure smoke test from application persistence.
- **Presentation dependencies appropriately gate issue details:** PT3.1 depends on M2 and explicitly stops issue-level UI pending G-16; PT3.2 and handoff tasks follow presentation. A decision resolving G-16 is not a dependency if the fallback is to keep the UI non-issue-level.
- **Traceability is primarily by scope prose, not per requirement:** The plan has an FR/SC treatment table, and the task list has a deferred-work register, but there is no explicit mapping from each PT task to the prototype-specific acceptance criteria or plan milestones beyond phase grouping. PT4.3 can capture this without implying deferred SCs passed.
- **Task list completion states are absent:** All entries describe planned work, but there is no status convention. This is acceptable for a plan, but do not treat tasks as completed until evidence exists.

### Dependency Clarifications Before Execution

1. **Toolchain selection:** Current criteria place version selection in PT0.3 before PT1.1, while the plan puts selection in Phase 1. Add a distinct toolchain-decision task or make the PT0.3 dependency and acceptance explicit; do not begin bootstrap until versions are recorded.
2. **PT0.4 timing:** Treat this analysis as a draft before scope resolution and revalidate it after PT0.1–PT0.3. This avoids an apparent circular gate while preserving PT0.4 as an M0 deliverable.
3. **PT1.2 value:** The constitution mandates PostgreSQL 15, but no prototype data is persisted. Keep the database task only as a required stack/infrastructure validation; do not expand it into Jira persistence.
4. **PT3.1 content:** Before starting UI implementation, explicitly decide the minimal data the demo presents. If no content beyond the mock-data notice is approved, do not invent dashboard summaries to make the screen appear complete.
5. **Evidence ownership:** PT4.3 should record checks and approved deferrals only. G-23 does not identify a sign-off owner, so the task must not manufacture one.

## Execution Guidance

- Start with PT0.1 because it is low-risk and prevents high-cost scope mistakes. Then resolve PT0.3/decision gates and PT0.2 before revalidating PT0.4 and accepting M0.
- Finish the toolchain prerequisite before PT1.1; follow the dependency chain rather than starting PostgreSQL, backend migrations, or documentation ahead of their prerequisites.
- Implement only local invented fixture behavior. No Jira/identity network calls, dashboard-data endpoints, Jira-like persistence, or scheduler are within this task list.
- Keep any display decision limited to fixture information that has been explicitly accepted; G-16 blocks issue-level UI, and G-08 leaves even aggregate presentation unspecified.
- At M4, report the prototype checks separately from the product's unfulfilled Jira, authentication, filter, metric, refresh, persistence, and external-user requirements.
